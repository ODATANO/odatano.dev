# API Reference

## In total: 6 services, 40 entities, 57 actions

The three client-facing services come first. The three ODATANO 2.0 operator services follow.

All entity sets support `$filter`, `$select`, `$expand`, `$top`, `$skip`, `$count`, `$orderby` \
Actions are POST with a JSON body. Functions are GET, marked _(GET)_ below \
Everything requires an authenticated user, except `VerifyDataSignature` and `getLiveness`. Admin-only actions are marked _(Admin)_

| Service | Path |
|---------|------|
| `CardanoODataService` | `/odata/v4/cardano-odata/` |
| `CardanoTransactionService` | `/odata/v4/cardano-transaction/` |
| `CardanoSignService` | `/odata/v4/cardano-sign/` |
| `CardanoIndexerService` | `/odata/v4/cardano-indexer/` |
| `CardanoWorkerService` | `/odata/v4/cardano-worker/` |
| `CardanoAgentService` | `/odata/v4/cardano-agent/` |

## CardanoODataService `/odata/v4/cardano-odata/`

## CardanoSignService `/odata/v4/cardano-sign/`

### Entities

`SigningRequests` · `SignatureVerifications` · `AddressSigningRequests` · `TransactionBuilds` · `TransactionSubmissions`

### Actions

**Workflow:**

| Action | Params | Returns |
|--------|--------|---------|
| `CreateSigningRequest` | `buildId: UUID`, `message: String` | `SigningRequests` |
| `GetSigningRequest` | `signingRequestId: UUID` | `SigningRequests` |
| `GetSigningRequestsByAddress` | `address: Bech32` | `AddressSigningRequests[]` |
| `VerifySignature` | `signingRequestId`, `signedTxCbor`, `signerType`, `signerInfo`, `address?` | `SignatureVerifications` |
| `SubmitVerifiedTransaction` | _(same 5 params)_, `deferSubmit?: Boolean` | `TransactionSubmissions` |
| `VerifyDataSignature` _(public)_ | `address: Bech32`, `coseSignature`, `coseKey`, `expectedPayload?` | `{ valid, reason, signedPayload, signerVkh }` |

**HSM (PKCS#11):**

| Action | Params | Returns |
|--------|--------|---------|
| `SignWithHsm` | `buildId: UUID`, `address?: Bech32` | `SigningRequests` |
| `SignAndSubmitWithHsm` | `buildId: UUID`, `address?: Bech32`, `deferSubmit?: Boolean` | `TransactionSubmissions` |
| `GetHsmStatus` | _-_ | `{ connected, keyId, keyLabel, publicKeyHash, cardanoAddress }` |

Optional `address` on the four signing actions enables consumer-side ownership verification.

`deferSubmit: true` verifies and claims on the caller's transaction, then submits after commit. The result comes back with status `pending`.

`VerifyDataSignature` checks a CIP-30 `signData` COSE_Sign1 signature against an address. It is public and stateless, so wallet login can call it before authentication.

Lifecycle: `created → pending → verified → submitted`.

## CardanoIndexerService `/odata/v4/cardano-indexer/`

ODATANO 2.0 service. Status and control for the chain crawler (pre-sync). Off by default, enable with `crawler.enabled`.

### Entities

| Entity | Description |
|--------|-------------|
| `SyncState` | Singleton crawl cursor: pre-sync progress, tip lag, status, errors |
| `ReorgLog` | Audit trail of chain rollbacks handled by the crawler |

### Actions

| Action | Params | Returns |
|--------|--------|---------|
| `getStatus` _(GET)_ | _-_ | `{ running, syncStatus, source, lastSlot, lastHeight, tipHeight, syncProgress, consecutiveErrors }` |
| `getLiveness` _(GET, public)_ | _-_ | `{ status, timestamp, uptime, version, network }` |
| `pauseCrawler` _(Admin)_ | _-_ | `Boolean` |
| `resumeCrawler` _(Admin)_ | _-_ | `Boolean` |

`getLiveness` answers 200 while the process runs. Use it for Docker `HEALTHCHECK` and gateway probes. `source` reports `chain-sync` or `pagination` for the crawling instance.

Events: `blockIndexed` after each committed block, `reorg` after a committed rollback. In-process consumers subscribe via `cds.connect.to('CardanoIndexerService')`.

## CardanoWorkerService `/odata/v4/cardano-worker/`

ODATANO 2.0 service. Runs build, sign, submit and confirm as one job on a server-side wallet. Keys never pass through this API. Off by default.

### Entities

| Entity | Description |
|--------|-------------|
| `WalletJobs` | Asynchronous wallet jobs. Non-admin callers see their own jobs only |
| `WorkerWallets` | Registered server-side worker wallets: addresses and stats, no key material |

### Actions

| Action | Params | Returns |
|--------|--------|---------|
| `SubmitWalletJob` | `walletId`, `kind`, `requestJson`, `idempotencyKey?`, `priority?`, `notBefore?` | `{ jobId, status, deduplicated }` |
| `CancelJob` | `jobId: UUID` | `Boolean` |
| `GetJobStatus` _(GET)_ | `jobId: UUID` | `{ jobId, walletId, kind, status, attempt, txHash, fee, errorCode, errorMessage, submittedAt, confirmedAt, finishedAt }` |
| `GetWorkerStatus` _(GET)_ | _-_ | `{ running, wallets, executing, awaitingConfirmation, pendingJobs }` |
| `PauseWorker` _(Admin)_ | _-_ | `Boolean` |
| `ResumeWorker` _(Admin)_ | _-_ | `Boolean` |

`kind` is one of `simpleAda`, `metadata`, `multiAsset`, `mint`, `plutusSpend`, `submitSigned`. `requestJson` carries the same payload as the matching Build action. `senderAddress` is always replaced by the wallet address.

`CancelJob` only works while a job is still pending. Jobs on HSM-backed wallets also require the configured `hsm.requiresRole`.

Events: `jobConfirmed` and `jobFailed` replace a `GetJobStatus` poll loop for in-process consumers.

## CardanoAgentService `/odata/v4/cardano-agent/`

ODATANO 2.0 service. Issues scoped, budgeted bearer tokens for AI agents. A request with the `x-agent-token` header runs as `agent:<grantId>` with role `agent-grant`. Off by default, enable with `agentGrants.enabled`.

### Entities

| Entity | Description |
|--------|-------------|
| `AgentGrants` | Issued grants without the token hash. Admins see all, a token sees its own row |

### Actions

| Action | Params | Returns |
|--------|--------|---------|
| `GetGrantStatus` _(GET)_ | _-_ | `{ grantId, agentLabel, allowedActions, walletId, allowedJobKinds, maxJobsPerDay, jobsUsedToday, budgetWindow, validUntil, isActive }` |
| `CreateAgentGrant` _(Admin)_ | `allowedActions`, `walletId?`, `allowedJobKinds?`, `maxJobsPerDay?`, `validUntil?`, `agentLabel?` | `{ grantId, token, allowedActions, walletId, allowedJobKinds, maxJobsPerDay, validUntil }` |
| `UpdateAgentGrant` _(Admin)_ | `grantId`, `agentLabel?`, `allowedActions?`, `allowedJobKinds?`, `maxJobsPerDay?`, `validUntil?` | `{ grantId, updated }` |
| `RotateAgentGrantToken` _(Admin)_ | `grantId: UUID` | `{ grantId, token }` |
| `RevokeAgentGrant` _(Admin)_ | `grantId: UUID` | `Boolean` |
| `GetGrantUsage` _(GET)_ | `grantId: UUID`, `since?`, `until?` | `{ grantId, since, until, calls[], total, jobsUsedToday, maxJobsPerDay }` |

The token is returned once by `CreateAgentGrant` and `RotateAgentGrantToken` and stored as SHA-256. `walletId` is required when `SubmitWalletJob` or `CancelJob` is allowed. The wallet binding cannot be changed later.

`GetGrantStatus` answers 400 without a token. `GetGrantUsage` covers at most 366 days, default the last 30. Admin actions are rate limited per principal, 10 per hour by default.
